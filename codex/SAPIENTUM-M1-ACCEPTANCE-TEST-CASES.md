**Документ:** `SAPIENTUM-M1-ACCEPTANCE-TEST-CASES.md`

## 1. Область и правила приёмки

**Что принимаем:** работоспособный **Synthetic MVP** для олимпиадного кружка: создание организации, пользователей, групп и курса; загрузка и публикация Markdown/ZIP; ученическое занятие; сдача нескольких фотографий; рецензирование пером; доработка и принятие; история, прогресс; корректный доступ и восстановление после ошибок/перезапусков.

**Что не принимаем в M1:** реальную обработку персональных данных детей, разрешение пилота, production cutover, эксплуатационные SLO/RPO/RTO, юридическую готовность по 152-ФЗ, fs-verity/kernel seal и доказательство физического завершения syscall, реальный сенсорный планшет (если его отдельно не испытывали), расширенную аналитику/календарь/родительский кабинет. Эти элементы не становятся PASS из-за удачных синтетических тестов.

**Приоритеты:** `P0` — блокирует итоговое `SYNTHETIC MVP ACCEPTED`; `P1` — обязателен для полноценной приёмки функций и UI, не закрытый P1 требует дефекта и явного решения владельца; `P2` — допустимое улучшение, не заменяет P0/P1. Нормативный owner gate нельзя обойти согласием тестировщика.

**Вердикты:** `PASS`, `FAIL`, `BLOCKED`, `NOT RUN`, `NOT APPLICABLE` (с доказанным основанием). Для визуального референса отдельно `REFERENCE AVAILABLE / REFERENCE UNAVAILABLE` — это не статус функционального теста. `PASS` присваивается только после исполнения указанного сценария с реальными HTTP/DB/file assertions. Нельзя засчитывать старый unit/component PASS вместо сквозной M1-11 проверки.

**Граница инструментов:** действия пользователя выполняются в **production React bundle через настоящий Chromium/HTTPS**; административный bootstrap — предусмотренный доверенный сценарий. SQL допустим как **независимый read-only oracle** после операций, но не для создания пользовательских курсов, зачислений, работ, отзывов и публикаций. Инъекция времени/сбоев допускается только изолированным тестовым harness, с явной пометкой. HTTP-негативы проверяются с реальными штатными сессиями, не доверяя присланному клиентом `organizationId`.

**Git и сохранность checkout:** при выполнении тестов фиксировать branch/HEAD, `git status`, `MERGE_HEAD`, состояние index; не удалять чужие unstaged файлы и не включать их в commit. По последнему отчёту остаются 14 нестейдженных PNG evidence M1-06/M1-07 — **перепроверить**, не предполагать, что их число осталось прежним. Push/deploy вне данного тестового задания запрещены без отдельного решения. Решение о commit M1-11 — отдельно.

## 2. Стандартная карточка и доказательства

У каждого кейса указаны: `ID`, `приоритет`, связь с `E01–E15` / `U01–U13`, предусловия, точные действия, ожидаемый результат и минимальный evidence. При выполнении дополнить **исполнителя, дату, environment build/HEAD, результат, defect ID, артефакты**.

Рекомендуемая строка в протоколе:

```text
TC-001 | PASS/FAIL/BLOCKED/NOT RUN | дата UTC | HEAD | Chromium build | evidence path | defect ID | примечание
```

**На каждый P0:** сохранённый route/user action, фактический HTTP outcome, сравнение с DB/file инвариантом и скриншот/лог. Для запрета проверять **отсутствие утечки**, а не только код ответа: тело, bytes, count, page totals, поиск, приватный asset и локальный cache. Все доказательства содержат только синтетические данные и не раскрывают настоящие одноразовые коды/пароли/refresh-токены.

## 3. Среда и тестовые данные

### 3.1. Среда

- Изолированный Linux synthetic runner с поддерживаемыми .NET, PostgreSQL, Node/React, Python compiler/importer, HTTPS и приватным file store.
- Реальный Chromium с production React bundle, контексты: platform operator, Org A admin, Org B admin, два преподавателя T-A/T-X и ученики.
- Старт через штатный runbook + миграции с **пустой** БД. Нельзя полагаться на невидимый первоначальный seed учебных сущностей. Допускается trusted bootstrap оператора согласно принятому owner contract.
- Хранить отдельные результаты логов: frontend/api/db/worker, HAR, screenshots, file checksums и snapshots. Для `E14/E15` подготовить **новое disposable окружение** под восстановление.
- Разные сценарии изменения состава/полномочий выполнять на независимых снимках исходной synthetic-конфигурации, иначе тесты меняют друг другу ожидаемые счётчики.

#### TC-001 · Чистый запуск на пустой PostgreSQL

**Приоритет:** `P0` · **Трассировка:** `E15`  
**Предусловия:** Базовая синтетическая среда из §3; данные теста изолированы от остальных сценариев.

**Шаги:**
1. Создать отдельное disposable synthetic-only окружение с пустой БД и приватным файловым хранилищем.
2. По runbook применить миграции, поднять PostgreSQL, API и production React bundle; открыть приложение в Chromium по HTTPS.

- Для первого bootstrap допустим только отдельно утверждённый trusted operator provisioning путь.

**Минимальные доказательства:** runbook, версии runtime, миграционный лог, HTTPS HAR, скриншот пустого состояния.  
**Факт / статус / ссылка на evidence / дефект:** `NOT RUN` · `—` · `—`
