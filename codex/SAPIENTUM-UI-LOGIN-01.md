## 1. Правки страницы `/login`

**1. Герой-текст (без изменения картинки).** Надпись «Олимпиадная математика» и подзаголовок «Задачи, кружки, прогресс и обратная связь в одном месте» в текущем скриншоте перекрывают контрастную листву. Переместить **оба HTML-текстовых блока**, не трогая рисунок: в свободную светлую область между логотипом и растениями. Сохранить смысл и видимую иерархию: заголовок в две строки, подзаголовок ниже. Ориентир исходного desktop-кадра (не жёсткие координаты): сместить copy правее левых листьев и несколько выше текущего положения, уменьшить max-width/размер только если необходимо. Проверить, что контрастных объектов под текстом нет при 1440, 1280, 768 и 390 px; для узких экранов использовать отдельную адаптивную компоновку (не накладывать текст на иллюстрацию). Никаких фоновых плашек поверх рисунка без согласования.

**2. Административные ссылки.** Убрать с публичного login ссылки «Первый запуск», «Первый администратор», «Оператор безопасности». Собрать их на **отдельной административной странице**, открываемой по непредсказуемому UUID URL, например `/<uuid-v4>`, с UUID, заданным безопасной серверной конфигурацией для окружения, а не жёстко прописанным в публичной странице, JS bundle или исходниках. Не выводить ссылку в публичной навигации/сайтмапе. Публичный посетитель не должен узнавать адрес через UI; неверный UUID — 404. **UUID является только сокрытием точки входа, НЕ авторизацией:** каждая операция должна продолжать требовать свои существующие проверки platform operator/bootstrap/security operator, scoped JWT или активации, CSRF/Origin и аудит; первоначальная настройка должна сохранять свой доверенный one-time/bootstrap механизм. Защитить административную страницу от индексации и утечки URL через внешние переходы/Referrer, не писать URL-секрет в открытые логи. Уточнить конкретные UI-маршруты при реальной реализации.

**3. Заголовок.** Заменить «Вход в Сапиентум» на **«Вход»**. Бренд слева оставить.

**4. Организация.** Поле «Организация» и любой ввод UUID удалить с формы. На форме — только «Логин», «Пароль», кнопка «Войти» (и релевантные элементы восстановления, если они уже есть в принятом процессе).

**5. Названия вместо GUID.** Во **всех пользовательских экранах выбора/смены/отображения организации** показывать её человекочитаемое название. UUID сохраняется во внутренних API, БД и привязках scopes; это не требование менять PK или миграции. Не показывать GUID обычным пользователям в заголовках, списках, breadcrumb, status, ошибках и доступных подписи полях. При совпадении названий использовать безопасную различимую подпись (например, город или тип, если действительно есть в данных), а не внутренний ID.

**6. Верхняя панель.** Удалить с `/login` «Помощь» и «RU», не добавлять заглушек/нерабочих кнопок.

**7. Иконки.** «Логин» — общепринятая `user-round` / `user`, «Пароль» — `lock-keyhole` / `lock`. Видимость пароля — `eye` / `eye-off` с доступным названием и переключаемым состоянием, не пустой кружок. Иконки декоративны для screen reader, labels остаются текстовыми.

**8. Активная сессия.** При открытии `/login` автоматически проверять действующую сессию через штатную защищённую refresh-cookie/session API и **без дополнительного нажатия** переводить в приложение/выбор организации. Пока проверка идёт, показывать короткое нейтральное loading state без flicker формы; при истечении/отзыве/отсутствии cookie показать форму. Убрать кнопку «Продолжить текущую сессию» и разделитель «или», если он больше не нужен. Сохранить cross-tab logout, очистку Blob URL/drafts, CSRF/Origin, отказ по revoke и защиту от refresh loop.

**9. Route.** Страница находится на **`/login`**, а не на `/courses`; `/courses` остаётся защищённым учебным каталогом. Неавторизованный заход в `/courses` переводит на `/login` с безопасным возвратом к исходному разрешённому deep link после входа. Logout возвращает на `/login`. Избегать redirect loop.

## 2. Сценарий входа без ввода организации

**Смысл:** принадлежность к организациям не должна подтверждаться знанием их UUID, но проверка пароля/личности и выдача полномочий сохраняются.

1. Пользователь открывает `/login` без действующей сессии; видит **только логин и пароль**.
2. Сервер проверяет учётные данные и реальную identity; **только после успешной проверки** получает разрешённые active OrganizationMembership, с названиями организаций, с учётом действующих ограничений. Не возвращать перечень организаций для произвольного введённого логина без подтверждения пароля.
3. **0 доступных организаций:** понятное безопасное сообщение «Нет доступных организаций. Обратитесь к администратору»; не создавать учебные grants.
4. **1 организация:** выбрать её автоматически, выдать существующую org-scoped сессию и перейти на учебную страницу, которую пользователь вправе открывать.
5. **2+ организации:** показывать отдельный экран `/select-organization` (или одобренный эквивалент) с карточками **названий**. После выбора выполнить штатную смену/активацию org scope; не сохранять пароль в URL, storage или React state дольше необходимого. Не выдавать course grants до подтверждения выбранного контекста.
6. **Уже активная сессия с выбранной org:** открытие `/login` автоматически перенаправляет в разрешённое приложение. Если актуальная сессия требует выбора организации — сразу на выбор; никакой промежуточной кнопки.
7. После смены организации: аннулировать/заменить прежний клиентский scoped контекст, запросы и временные Blob URLs; не показывать cached courses/files предыдущей организации.
8. Если backend сейчас требует `organizationId` уже на `login`, реализовать только **договорённый минимальный безопасный серверный протокол** (например, короткоживущий credential-verified ticket с серверной привязкой к identity и защищённым completion шагом). Не заменять его неаутентифицированным `GET organizations?login=...`, не посылать пароль по организациям в цикле и не хранить access JWT в localStorage. Сначала сверить ограничения `AGENTS.md` и получить недостающую owner authorization на точные HTTP изменения при необходимости.

## 3. Дополнительный экран выбора организации (обязателен для multi-org)

- Тот же визуальный язык Sapientum: светлый фон, белая карточка, зелёные действия; заголовок **«Выберите организацию»**; краткая инструкция.
- Отобразить **только разрешённые** для identity организации по человекочитаемому названию. Карточка: название, при необходимости разрешённое уточнение; не показывать GUID.
- Различать «Выбрать», «Выйти» / «Войти в другой аккаунт»; выбор переключает контекст по существующей строгой модели авторизации.
- При потере сессии, отсутствии активного membership, revoke/ProcessingRestrictions — безопасное состояние; не подменять новым tenant из старого localStorage.
- На телефонном экране карточки в одну колонку. Достаточные размеры кнопок, tab/keyboard focus, screen reader labels.

## 4. Проверки и обязательная приёмка

1. **Визуально:** оригинальный `login-study-room.png` побайтно неизменен (SHA-256); надписи не перекрываются с листьями на 1440/1280 и адаптивных 768/390; скриншоты. Нет Help/RU, admin links, org field, continue-session button. Заголовок «Вход», стандартные иконки.
2. **Маршрутизация:** `/login` — единственная страница входа; `/courses` доступен только после scoped login; redirect back безопасен; нет цикла.
3. **Одна организация:** login/password → каталог без промежуточного выбора; виден **name**, не GUID.
4. **Несколько организаций:** login/password → `/select-organization` → выбрать по названию → курсы выбранной; после switch данные чужой организации не отображаются.
5. **Активная сессия:** переход сразу из `/login` в приложение без click; reload, expiry/refresh, cross-tab logout и server revoke — корректно.
6. **Ошибочный логин/пароль:** неизвестный логин не выдаёт список организаций, нет утечки существования аккаунтов через разные ответы и timing за рамками принятых защит, есть внятная ошибка.
7. **Secret admin URL:** ссылки исчезли с `/login`; неверный UUID → 404; известный URL без полномочий не даёт выполнять admin/security операции, доступ разрешённым operator/role/bootstrap работает; нет shortcut через legacy URL.
8. **RBAC:** org A не показывает организации/материалы org B; zero memberships, withdrawn membership и ProcessingRestrictions обработаны fail-closed.
9. **Безопасность:** нет password/JWT в URL/localStorage, CSRF/Origin действуют, session audit не ослаблен, нет auth bypass в admin route; авторизация проверяется сервером.
10. **Регрессия:** действующие .NET auth/API и frontend suites + отдельный реальный Chromium HTTPS E2E с single-org, multi-org, login, org selection, session reuse, logout. Закрыть opt-in browser suites, если затронуты. Указать PASS/FAIL/SKIP с доказательствами.
11. **UI evidence:** по крайней мере `/login` 1440 и 390, `/select-organization` 1440 и 390, вход и автоматическое восстановление, административный маршрут в авторизованном контексте (без публикации самого секретного UUID в отчёте).
