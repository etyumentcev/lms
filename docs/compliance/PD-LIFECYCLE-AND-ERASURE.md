# L0.1 — Lifecycle, уничтожение и восстановление

**PROPOSAL**, [ADR-L09](../adr/ADR-L09-personal-data-lifecycle.md), [ADR-L10](../adr/ADR-L10-erasure-and-immutable-history.md); PD-G02/03/07/08/09 должны быть согласованы. Источники и сроки [R10–R13](PD-LEGAL-REQUIREMENTS.md) имеют статус **LEGAL SOURCE NOT VERIFIED**. Числа ниже — кандидаты правового SLA, не утверждённый регламент. Отдельные рабочие/календарные дни не взаимозаменяемы.

## Различия операций

Деактивация запрещает вход; отзыв полномочий меняет grants; блокирование прекращает обработку указанного набора/цели на время проверки (кроме допустимых операций уточнения); прекращение обработки останавливает цель; удаление логической строки не гарантирует уничтожение; уничтожение должно исключить восстановление содержания в применимом объёме; обезличивание требует проверки невозможности определить принадлежность без дополнительной информации и применимого режима. UUID/хеш/удаление IdentityUser остаются связуемыми. Retention/hold имеет собственное основание, цель, срок, разрешённый доступ и пересмотр.

## Процессы и доказательства

Case register и следующие workflows отсутствуют; предлагаемые имена не существующие классы. Каждый case: ID, receivedAt, verified subject/representative reference, цель/категории, причина, applicable rule/version, deadline/timezone/calendar, owner/backup owner, действия/status, ссылки evidence, approved exceptions с отдельным сроком. Телефон/адрес такого канала пока UNKNOWN, политика не публикуется с фиктивными реквизитами.

## Уничтожение: последовательность PROPOSAL

1. ПД подтверждает запрос, правовое основание/срок и объём; юрист разбирает mixed-subject work/retention, reviewer согласует manifest. Issuer не вправе удалить историю просто по просьбе Teacher.
2. Зарегистрировать intent во внешнем актуальном журнале исполнения до разрушительных действий. Privacy block независимо от active account и enrollment: course-wide Teacher иначе продолжает читать. Приостановить affected reads/writes, drain; согласовать global barrier с backup/deploy/cleanup. При неопределённом статусе не открывать доступ.
3. Dry-run closure: Identity/mapping/grants, назначения/work, Submissions/Reviews/Messages/ReplyTo, annotations JSONB, DomainEvents.Payload, attachment arrays, StoredAttachments/AccessAttachments/physical keys; также free text/EXIF/roster/log exports/shared content. Поиск только по StudentId недостаточен. Определить затронутых других субъектов и правомерные holds.
4. Утвердить неизменяемый manifest (digest, scope, версия схемы, причина, ожидаемые counts и зависимости). Использовать отдельный временный executor, способный выполнить только утверждённый план. Никакого универсального флага bypass у app role.
5. Выполнить транзакционную DB-часть в порядке FK с отдельным защищённым путём triggers; файл/DB не одна транзакция — durable task manifest, идемпотентные шаги и блокирование до завершения всех. Не удалять все работы учеников автоматически при увольнении преподавателя: сначала определить законно сохраняемые связи и отдельный способ минимизации. Точное изменение triggers/DDL — будущий reviewed design/test, сейчас отсутствует.
6. Удалить originals/temp/копии/производные, обработать backups/WAL/provider snapshots. Записать успех каждого store или ошибку/next retry/deadline. FS unlink/SQL DELETE не доказывает исчезновение с underlying media; provider/носитель/шифрование и ключи входят в evidence.
7. Проверить отсутствие по manifest и negative API queries, reconcile byte counts, получить подтверждения подрядчиков. Сформировать акт + выгрузку журнала с обязательными полями по действующему приказу 179; для невозможной части статус BLOCKED/INCOMPLETE и правовое решение, не COMPLETE.
8. Завершить запрос/уведомления, оставить минимум evidence на отдельном основании. В surviving aggregates нет invented replacement «анонимный пользователь» без доказательства. История обычных не затронутых работ не изменяется.

## Backup / restore: защита от возвращения ПД

**FACT:** operational backup/restore нет; [ADR-L05](../adr/ADR-L05-backup-restore.md) — проект, K-S06 открыт. RPO/RTO/окно/retention **UNKNOWN**, решает владелец. Off-host encryption рекомендовано, не доказано.

PROPOSAL: журнал исполнения запросов содержит case/sequence, scope digest, affected opaque references, тип revoke/block/erase, effectiveAt, state, hold/deadline, evidenceRef; отдельный журнал уничтожения фиксирует store/set/action/time/result/executor/verifier. Это ПД, включая hash/UUID; ограничить доступ, регион/retention и не хранить raw content. Хранить актуальный журнал вне rollback-domain LMS, с независимой защищённой репликацией/backup в РФ и контролем целостности. Он не просто восстанавливается из того же старого snapshot. Срок ledger покрывает все потенциально восстанавливаемые копии и отдельно правовые evidence; retired IDs можно убрать после доказанного уничтожения всех старых наборов и обязательного срока. Потеря актуальности ledger блокирует restore cutover.

Для каждого backup set хранить cutoff sequence, состав DB/files/schema/key versions, проверенные hashes и место каждой копии. Удаление в активной БД не завершает erasure при сохраняющейся расшифровываемой копии. Предпочтительно до deadline удалить затронутый set/пересобрать согласованную очищенную копию и подтвердить удаление всех replicas. Если provider immutable lock делает это невозможным, не выбирать такой режим без доказанного законного срока/основания. Crypto-erasure допустима только после анализа алгоритма, key isolation, всех escrow/кэшей и правовой допустимости; общий ключ backup нельзя удалить без оценки потери всех остальных данных.

Restore runbook:

1. Закрытый quarantine host, public ingress и обычные credentials выключены; минимальные restore operators, журнал доступа. Само восстановление — обработка, правовое основание и ограничение цели должны быть предусмотрены до загрузки старых ПД; quarantine не легализует хранение автоматически.
2. Получить **актуальный** ledger/high-watermark из независимого источника; проверить подпись/целостность/непрерывность/age и контрольную запись. Если недоступен/устарел — fail closed, не обещать достигнутый RTO.
3. Восстановить согласованный DB/files set, миграции/triggers/keys; не разрешать jobs/экспорты. Отозвать все старые сессии/challenges, сверить действующие grants/представительство/consent/holds с актуальным реестром.
4. Применить все block/revoke/erasure intents после cutoff, включая незавершённые intents (не только COMPLETE). Выполнить reconciled deletion и проверить отсутствие в metadata/файлах/events/text/annotations/read projections; повторное исполнение безопасно.
5. Под barrier получить последний watermark вновь, применить хвост; reviewer сверяет counts/negative tests и manifest, ПД разрешает обработку, ops cutover. Новый snapshot только после reconciliation. Сетевой доступ не включается кнопкой «restore succeeded».
6. Удалить quarantine temp/старые copies в согласованные сроки, оформить акт/drill и measured full RTO/RPO. Нельзя считать baseline restore counts, включавшие уничтоженные работы, обязательными после правомерного erasure: изменение объясняет manifest.

Acceptance L3/L4: snapshot до удаления ученика и до отзыва teacher grant; новые запросы во время restore; старый consent/старые session keys; отсутствующий ledger; частичный unlink; corrupted set; повтор job; provider copy. Проверить, что ни один публичный запрос не получил старые ПД. Все сценарии пока NOT VERIFIED.
