# LMS MVP — Actors and Use Cases

**Status:** Draft  
**Version:** 1.0  
**Scope:** первый рабочий релиз LMS олимпиадного кружка

---

# 1. Цель MVP

MVP должен закрывать полный основной учебный цикл:

> преподаватель публикует учебные материалы → ученик изучает урок → решает задачу → отправляет решение → преподаватель проверяет → ученик при необходимости дорабатывает решение → задача засчитывается → прогресс обновляется.

MVP не должен превращаться в универсальную LMS или CMS.

Учебный контент создаётся вне приложения и хранится в Markdown в соответствии с `COURSE-CONTENT-SPEC.md`.

---

# 2. Actors

В MVP существуют две пользовательские роли.

## 2.1. Student

**Student** — ученик, зачисленный в один или несколько курсов.

Student может:

- видеть доступные ему курсы;
- открывать курс;
- открывать опубликованные уроки;
- читать материалы урока;
- открывать задачи;
- видеть состояние каждой задачи;
- отправлять решение;
- прикладывать фотографии и файлы;
- использовать Markdown и LaTeX в сообщении;
- отвечать преподавателю;
- цитировать сообщения;
- отправлять новую попытку после замечаний;
- видеть историю решения задачи;
- видеть свой прогресс по уроку и курсу.

Student MUST NOT:

- изменять материалы курса;
- видеть неопубликованные уроки;
- видеть решения других учеников;
- видеть преподавательские данные других учеников;
- менять статус задачи напрямую;
- отмечать собственное решение как `Accepted`.

---

## 2.2. Teacher

**Teacher** — преподаватель курса или группы.

Teacher может:

- видеть курсы, к которым имеет доступ;
- публиковать подготовленную версию курса;
- публиковать/открывать урок для учеников;
- видеть учеников курса или группы;
- видеть очередь решений на проверку;
- открывать историю работы ученика над задачей;
- просматривать текст решения и вложения;
- писать сообщения с Markdown и LaTeX;
- цитировать сообщения ученика;
- ставить `Accepted`;
- ставить `NeedsRevision`;
- видеть прогресс учеников;
- видеть агрегированный прогресс группы.

Teacher MUST NOT:

- изменять опубликованную историческую версию задачи задним числом;
- удалять историю попыток так, чтобы она становилась недоступной для аудита;
- менять авторство сообщений;
- подменять текст ранее отправленного учеником решения.

---

# 3. Основной объект взаимодействия

Центральным объектом LMS является не урок и не домашняя работа целиком, а:

> **работа конкретного ученика над конкретной назначенной задачей.**

Концептуально:

```text
Student
   +
ProblemAssignment
   ↓
ProblemWork
   ├── Submission #1
   ├── Teacher Message
   ├── Submission #2
   ├── Teacher Message
   └── Review
```

История работы MUST сохраняться.

---

# 4. Основной end-to-end сценарий

```text
Teacher
  ↓
Publishes course version
  ↓
Publishes lesson
  ↓
Student opens lesson
  ↓
Student opens problem
  ↓
Student submits solution
  ↓
Problem status = Submitted
  ↓
Teacher sees item in review queue
  ↓
Teacher reviews
  ├── Accepted
  │      ↓
  │   Problem completed
  │
  └── NeedsRevision
         ↓
      Student receives feedback
         ↓
      Student submits new attempt
         ↓
      Submitted
         ↓
      Teacher reviews again
```

# 5. Use Cases — Student

## UC-S01. View my courses

### Goal

Ученик открывает список доступных ему курсов.

### Preconditions

- пользователь аутентифицирован;
- пользователь имеет роль `Student`.

### Main flow

1. Student открывает LMS.
2. LMS получает активные зачисления пользователя.
3. LMS показывает список доступных курсов.
4. Для каждого курса показывается краткий прогресс.

### Result

Student может перейти к экрану курса.

---

## UC-S02. Open course

### Goal

Ученик открывает курс и видит его структуру.

### Preconditions

- Student зачислен на курс;
- существует опубликованная версия курса.

### Main flow

1. Student выбирает курс.
2. LMS показывает описание курса.
3. LMS показывает список доступных уроков.
4. Для каждого урока показывается состояние и прогресс.

### Business rules

Student MUST NOT видеть урок, если он ещё не опубликован или не открыт для него.

---

## UC-S03. Open lesson

### Goal

Ученик изучает материалы урока.

### Main flow

1. Student выбирает урок.
2. LMS загружает опубликованную версию `lesson.md`.
3. Markdown отображается через безопасный renderer.
4. LMS показывает:
   - текст;
   - формулы;
   - изображения;
   - ссылки;
   - видео;
   - файлы;
   - список задач.
5. Для каждой задачи показывается её текущее состояние.

### Result

Student может открыть конкретную задачу.

---

## UC-S04. Open problem

### Goal

Ученик открывает рабочую область задачи.

### Main flow

1. Student выбирает задачу.
2. LMS показывает опубликованное условие `problem.md`.
3. LMS показывает статус задачи.
4. LMS показывает историю работы над задачей.
5. LMS показывает форму новой попытки или ответа.

### Important

Условие MUST соответствовать той опубликованной версии, к которой привязано назначение.

---

## UC-S05. Submit solution

### Goal

Ученик отправляет попытку решения.

### Input

Student MAY отправить:

- Markdown-текст;
- LaTeX-формулы;
- фотографии;
- файлы.

Минимум одно содержимое MUST присутствовать:

```text
BodyMarkdown != empty
OR
Attachments.Count > 0
```

### Main flow

1. Student вводит сообщение.
2. При необходимости прикладывает файлы.
3. Student нажимает `Отправить решение`.
4. LMS валидирует вложения и Markdown.
5. LMS создаёт новую `Submission`.
6. LMS фиксирует время отправки.
7. Статус работы становится `Submitted`.
8. Решение появляется в очереди преподавателя.

### Postconditions

- Submission является неизменяемой исторической попыткой;
- Teacher может начать проверку.

### Invariants

Student MUST NOT изменять содержимое уже отправленной попытки так, чтобы терялась исходная версия.

Редактирование, если будет поддерживаться, MUST сохранять audit history.

---

## UC-S06. Reply to teacher

### Goal

Ученик отвечает на комментарий преподавателя.

### Input

Сообщение MAY содержать:

- Markdown;
- LaTeX;
- цитату;
- `ReplyToMessageId`;
- вложения.

### Main flow

1. Student нажимает `Ответить`.
2. LMS связывает сообщение с исходным `Message`.
3. Student вводит ответ.
4. LMS сохраняет сообщение в том же thread.

### Important

Обычное сообщение в диалоге не обязательно является новой попыткой решения.

---

## UC-S07. Submit revised solution

### Goal

Ученик отправляет новую попытку после `NeedsRevision`.

### Preconditions

Текущий статус:

```text
NeedsRevision
```

### Main flow

1. Student читает комментарий преподавателя.
2. Student дорабатывает решение.
3. Student отправляет новую попытку.
4. LMS создаёт новую `Submission`.
5. Предыдущие попытки сохраняются.
6. Статус становится `Submitted`.

---

## UC-S08. View progress

### Goal

Ученик видит состояние своей работы.

LMS SHOULD показывать:

### По уроку

```text
Accepted:       3
Submitted:      2
NeedsRevision:  1
NotStarted:     2
```

### По курсу

- количество доступных уроков;
- количество завершённых уроков;
- количество назначенных задач;
- количество зачтённых задач.

Прогресс MUST вычисляться из состояния учебного процесса, а не храниться как вручную изменяемый процент.

---

# 6. Use Cases — Teacher

## UC-T01. Publish course version

### Goal

Преподаватель публикует подготовленную версию Markdown-курса.

### Preconditions

- исходный курс доступен системе импорта;
- Teacher имеет право публикации.

### Main flow

1. Teacher инициирует публикацию.
2. LMS импортирует контент.
3. Запускается `CourseValidator`.
4. При наличии `ERROR` публикация прекращается.
5. При успешной проверке создаётся immutable published version.
6. LMS сохраняет идентификатор версии и source revision/commit.

### Result

Версия курса доступна для дальнейшего назначения и публикации уроков.

---

## UC-T02. Publish lesson

### Goal

Сделать урок доступным ученикам.

### Preconditions

- существует опубликованная версия курса;
- урок присутствует в этой версии.

### Main flow

1. Teacher выбирает урок.
2. Teacher выполняет `Publish/Open lesson`.
3. LMS создаёт или изменяет состояние доступности урока.
4. Student получает доступ к уроку.

### Important

Публикация урока является состоянием LMS, а не изменением `lesson.md`.

---

## UC-T03. View review queue

### Goal

Преподаватель видит решения, требующие проверки.

### Queue SHOULD содержать

- ученика;
- курс;
- урок;
- задачу;
- время отправки;
- номер попытки;
- возраст решения в очереди.

### Основной критерий попадания

Работа находится в состоянии:

```text
Submitted
```

### Teacher MAY

- открыть работу;
- фильтровать по курсу;
- фильтровать по группе;
- фильтровать по ученику.

Сложная сортировка и SLA не являются обязательными для MVP.

---

## UC-T04. Review submission

### Goal

Преподаватель проверяет очередную попытку решения.

### Main flow

1. Teacher открывает работу.
2. LMS показывает:
   - условие задачи;
   - текущую попытку;
   - вложения;
   - предыдущие попытки;
   - диалог.
3. Teacher изучает решение.
4. Teacher может написать комментарий.
5. Teacher выбирает результат:
   - `Accepted`;
   - `NeedsRevision`.

---

## UC-T05. Request revision

### Goal

Вернуть решение ученику на доработку.

### Preconditions

Существует submission в состоянии проверки.

### Main flow

1. Teacher пишет комментарий.
2. Teacher выбирает `NeedsRevision`.
3. LMS сохраняет review.
4. Статус работы становится `NeedsRevision`.
5. Работа исчезает из активной очереди `Submitted`.
6. Student видит замечание и возможность новой попытки.

### Rule

Комментарий SHOULD объяснять, что требуется пересмотреть, но педагогический стиль не является частью технического инварианта.

---

## UC-T06. Accept solution

### Goal

Засчитать задачу.

### Main flow

1. Teacher проверяет последнюю попытку.
2. При необходимости пишет комментарий.
3. Teacher выбирает `Accepted`.
4. LMS сохраняет review.
5. Работа становится `Accepted`.
6. Обновляется вычисляемый прогресс ученика.

### Invariant

Только Teacher с соответствующим доступом MAY переводить работу в `Accepted`.

---

## UC-T07. Reply in discussion

Teacher MAY отвечать ученику без изменения статуса работы.

Например:

```text
Student: Я не понимаю, почему здесь число обязательно чётное.

Teacher: Посмотри на остатки по модулю 2.

Student: Тогда получается...
```

Такие сообщения являются частью thread, но не должны автоматически создавать Review.

---

## UC-T08. View student progress

Teacher видит прогресс конкретного ученика по курсу.

Минимально:

- уроки;
- задачи;
- статусы задач;
- число попыток;
- время последней активности.

---

## UC-T09. View group progress

Teacher видит агрегированное состояние группы.

Минимальный MVP может показывать таблицу:

```text
Student       Accepted   Submitted   Revision   Not started
Иванов           12          2          1           5
Петров           15          0          2           3
...
```

Расширенная аналитика не входит в MVP.

---

# 7. Состояния работы над задачей

Для MVP фиксируется следующий state machine:

```text
NotStarted
     │
     │ submit
     ▼
Submitted
  │       │
  │       │ teacher requests revision
  │       ▼
  │  NeedsRevision
  │       │
  │       │ new submission
  │       └───────────► Submitted
  │
  │ teacher accepts
  ▼
Accepted
```

## 7.1. NotStarted

Ученик ещё не отправлял решение.

## 7.2. Submitted

Последняя попытка отправлена и ожидает решения преподавателя.

## 7.3. NeedsRevision

Преподаватель проверил решение и запросил доработку.

## 7.4. Accepted

Задача зачтена.

---

# 8. Переходы состояний

Разрешены:

```text
NotStarted     -> Submitted
Submitted      -> Accepted
Submitted      -> NeedsRevision
NeedsRevision  -> Submitted
```

В MVP SHOULD NOT быть ручного произвольного переключателя статусов.

Например:

```text
NotStarted -> Accepted
```

MUST NOT происходить через обычный student flow.

Если позднее потребуется административное ручное засчитывание, это должен быть отдельный Use Case.

---

# 9. Submission и Message — разные понятия

Это обязательное различие.

## Submission

`Submission` означает:

> ученик заявляет новую попытку решения задачи.

Пример:

```text
Submission #1
Submission #2
Submission #3
```

Submission влияет на state machine.

## Message

`Message` означает:

> реплика участника в обсуждении.

Примеры:

- вопрос ученика;
- уточнение преподавателя;
- короткий ответ;
- цитирование части предыдущего сообщения.

Message сам по себе MUST NOT менять статус задачи.

---

# 10. Review

Review — решение преподавателя по конкретной попытке.

Минимальная модель:

```text
Review
- Id
- SubmissionId
- TeacherId
- Decision
- MessageId?
- CreatedAt
```

`Decision`:

```text
Accepted
NeedsRevision
```

Review MUST ссылаться на конкретную `Submission`.

---

# 11. Базовые инварианты MVP

1. Student MUST иметь доступ только к назначенным ему курсам/группам.
2. Student MUST NOT видеть неопубликованный урок.
3. Student MUST NOT видеть чужие submissions.
4. Submission MUST принадлежать конкретному Student и конкретному ProblemAssignment.
5. Submission MUST быть исторически связан с версией условия задачи.
6. Новая попытка MUST NOT уничтожать предыдущую.
7. Teacher MUST иметь право на проверку соответствующей группы/курса.
8. `Accepted` и `NeedsRevision` MUST создаваться только через Teacher Review.
9. Одна опубликованная версия контента MUST быть immutable.
10. Изменение Markdown после публикации MUST NOT менять старые попытки ретроактивно.
11. Message MUST сохранять автора и время создания.
12. Attachment MUST проходить проверку доступа.
13. Markdown MUST проходить безопасный rendering.
14. Прогресс MUST вычисляться из фактического состояния задач.
15. Смена статуса MUST быть воспроизводима из истории событий/проверок.

---

# 12. Что не входит в MVP

В первый релиз НЕ входят:

- отдельный Admin UI;
- визуальный редактор курса;
- WYSIWYG редактор Markdown;
- рейтинги;
- баллы и геймификация;
- лайки задач;
- автоматическая проверка математических решений;
- AI-проверка решений;
- индивидуальная адаптивная траектория;
- сложная аналитика компетенций;
- родительский кабинет;
- мобильное приложение;
- push-уведомления;
- email-рассылки;
- календарь;
- видеоконференции;
- чат общего курса;
- peer review;
- ручное конструирование курса в UI;
- сложная ролевая модель.

Эти функции MAY быть добавлены после подтверждения основного рабочего цикла.

# 13. Минимальные экраны MVP

Из Use Cases непосредственно следуют 6 основных экранов.

## Student

1. **Course screen**
   - описание;
   - список уроков;
   - прогресс.

2. **Lesson screen**
   - Markdown-материал;
   - видео;
   - файлы;
   - список задач;
   - статусы.

3. **Problem workspace**
   - условие;
   - история попыток;
   - диалог;
   - вложения;
   - новая попытка.

## Teacher

4. **Review queue**
   - список ожидающих решений.

5. **Review workspace**
   - условие;
   - текущая попытка;
   - предыдущие попытки;
   - диалог;
   - `Accepted`;
   - `NeedsRevision`.

6. **Student/group progress**
   - статусы задач;
   - агрегированный прогресс.

---

# 14. MVP acceptance criterion

MVP считается функционально завершённым, если возможно выполнить сценарий:

1. Teacher публикует валидный Markdown-курс.
2. Teacher открывает урок.
3. Student видит урок.
4. Student открывает задачу.
5. Student отправляет решение с формулой и фотографией.
6. Teacher видит решение в очереди.
7. Teacher цитирует часть сообщения и отправляет замечание.
8. Teacher ставит `NeedsRevision`.
9. Student видит замечание.
10. Student отправляет вторую попытку.
11. Teacher ставит `Accepted`.
12. Student видит задачу как зачтённую.
13. Прогресс урока и курса обновляется.
14. История обеих попыток и всех сообщений сохраняется.
15. Условие задачи остаётся тем, которое было назначено ученику на момент работы.

Если этот цикл работает надёжно, первый вертикальный срез LMS реализован.
